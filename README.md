# PAC Activity Submission Form

A browser-based form for submitting POGIL activities to the POGIL Activity Clearinghouse (PAC). Authors fill out the form, which adapts to their submission kind and activity readiness, then download a PDF and JSON of their submission. A planned Cloudflare Worker integration (in trial) will eventually create the corresponding OJS submission automatically.

Hosted on GitHub Pages: `https://sgarrettroe.github.io/pac-submission-form/`

---

## Architecture

```
structure.xlsx          ← human-editable form specification (source of truth)
      ↓
build_schema.py         ← validates structure.xlsx, emits form-schema.json
      ↓
form-schema.json        ← runtime schema read by index.html
      ↓
index.html              ← browser-based form renderer (fetches form-schema.json at load)
      ↓
pac-ojs-worker.js       ← [TRIAL] Cloudflare Worker: proxies form submissions to OJS
```

No server, no database. Everything runs in the author's browser or in Cloudflare's edge network. GitHub Pages serves all static files.

## Files

| File | Purpose |
|---|---|
| `structure.xlsx` | Form specification — sections, fields, branching logic, PDF layout. **Edit this to change the form.** |
| `build_schema.py` | Python script that reads `structure.xlsx` and writes `form-schema.json`. Run manually or via GitHub Actions. |
| `form-schema.json` | Compiled schema. **Do not edit by hand** — generated by `build_schema.py`. Committed to the repo so GitHub Pages can serve it. |
| `index.html` | The form itself. Fetches `form-schema.json` at load time and renders the form dynamically. Also handles PDF/JSON generation, validation, and JSON save/reload. |
| `pac-ojs-worker.js` | Cloudflare Worker source. **See OJS Integration section below.** Safe to commit — contains no secrets. |
| `.github/workflows/build-schema.yml` | GitHub Actions workflow. Automatically rebuilds `form-schema.json` when `structure.xlsx` or `build_schema.py` is pushed. |

## Editing the Form

The form content is entirely driven by `structure.xlsx`. You do not need to touch `index.html` or `build_schema.py` for ordinary content changes.

### Spreadsheet sheets

| Sheet | Purpose |
|---|---|
| `ReadMe` | Explains every column and convention. Read this first. |
| `KindAxes` | Which fields act as "kind axes" — their option values drive section/field visibility. Currently `review_kind` and `readiness`. |
| `Sections` | One row per section. `applies_to_kinds` controls which axis values make a section visible. |
| `RepeatGroups` | Defines repeatable blocks (Authors, Learning Objectives, Images). |
| `Fields` | One row per question. Controls label, type, required-ness, branching (`show_if`, `disabled_if`), and which submission kinds it applies to. |
| `PDF_Layout` | Optional overrides for PDF page breaks and field rendering format. |

### show_if / disabled_if syntax

```
field_id == 'value'         radio/select equals
field_id != 'value'         radio/select not equals
field_id in [a,b,c]         radio/select: value is one of these
field_id not_in [a,b,c]     radio/select: value is NOT one of these
field_id all [a,b,c]        checkbox_group: every value is checked
field_id not_all [a,b,c]    checkbox_group: at least one value is NOT checked
```

### Edit workflow

1. Edit `structure.xlsx`
2. Commit and push to `main`
3. GitHub Actions automatically runs `build_schema.py` and commits the updated `form-schema.json`
4. GitHub Pages serves the new schema within ~60 seconds — no manual steps needed

To run the build locally:
```bash
pip install openpyxl
python build_schema.py structure.xlsx form-schema.json
```

## GitHub Actions

Defined in `.github/workflows/build-schema.yml`.

**Triggers:**
- Push to `main` that changes `structure.xlsx` or `build_schema.py`
- Manual trigger from the GitHub Actions tab

**What it does:**
1. Checks out the repo
2. Installs `openpyxl`
3. Runs `build_schema.py structure.xlsx form-schema.json`
4. Commits the updated `form-schema.json` back to `main` (only if the content actually changed)

The commit message includes `[skip ci]` to prevent the commit itself from triggering another workflow run.

**No secrets are needed** — the workflow uses the automatically-available `GITHUB_TOKEN` for the commit push.

## Developer flags in index.html

Near the top of the `<script>` block in `index.html`, two flags control debug output:

```js
const SHOW_SECTION_DEBUG_NOTES = false;  // "Always shown." / "Shown when: ..." under section headings
const SHOW_DEBUG_PANEL = false;          // raw answers/groupInstances dump at page bottom
```

Flip either to `true` while debugging branching logic. Set back to `false` before committing.

## OJS Integration (Blocked — Cloudflare WAF)

**Status: Abandoned for now.** The Worker code is written, deployed to `https://pac-ojs-proxy.sgarrettroe.workers.dev`, and structurally correct — but it cannot reach the OJS API due to a Cloudflare WAF configuration issue outside our control.

### What happened

`pac.pogil.org` sits behind Cloudflare's **Managed Challenge** (bot protection), which blocks all non-browser HTTP requests to `/api/v1/*`. This includes requests from Cloudflare Workers, even though the Worker runs inside Cloudflare's own network.

The fix requires a **WAF Custom Rule** on the `pac.pogil.org` Cloudflare account that exempts Worker traffic from the bot challenge:

- Condition: `cf.worker.upstream_used eq true` AND `http.request.uri.path starts_with "/index.php/pac/api/v1"`
- Action: **Skip → Bot Fight Mode**

We do not have access to the Cloudflare account managing `pac.pogil.org`. Until someone with that access adds the rule, the Worker cannot reach OJS.

### To resume this work

1. Get the WAF rule above added by whoever manages the `pac.pogil.org` Cloudflare account (hosting provider or PAC IT)
2. The Worker is already deployed — retest with the browser console fetch in `about:blank`:
   ```js
   fetch('https://pac-ojs-proxy.sgarrettroe.workers.dev/submit', {
     method: 'POST',
     headers: { 'Content-Type': 'application/json' },
     body: JSON.stringify({
       title: 'Test Submission via Worker',
       review_kind: 'traditional_review',
       readiness: 'activity_for_review',
       authors: [{ author_name: 'Test Author', author_email: 'test@test.com' }]
     })
   }).then(r => r.json()).then(console.log)
   ```
3. If the response contains `submissionId` and `workflowUrl`, the Worker is working and the next step is wiring up a "Submit to PAC" button in `index.html`

### What the Worker does (for reference)

`pac-ojs-worker.js` is a Cloudflare Worker proxy that:
1. Accepts a POST from `index.html` with PAC form data as JSON
2. Maps `review_kind` → OJS `sectionId`
3. Creates a bare OJS submission (`POST /submissions`)
4. Creates a publication (`POST /submissions/{id}/publications`) — required separately in OJS 3.3
5. Adds all authors (`POST /submissions/{id}/publications/{pubId}/contributors`)
6. Returns the OJS author workflow URL

### Section ID mapping (for reference)

| PAC `review_kind` | OJS section | `sectionId` |
|---|---|---|
| `traditional_review` | Activities for Traditional Review | 13 |
| `collaborative_peer_feedback` | Activities for Collaborative Peer Feedback (CPF) | 12 |
| `classroom_testing` | Activities for Classroom Testing Review | 15 |
| `activity_idea` | Activity Ideas | 3 |

### Known OJS 3.3 quirks (for reference)

- `POST /submissions` does not auto-create a publication in OJS 3.3 (fixed in 3.4)
- Contributor locale fields use bracket notation: `"givenName[en_US]"` not `{"givenName": {"en_US": "..."}}`
- Several 3.4+ endpoints do not exist in 3.3: `/sections`, `/contributors` as GET, etc.
- The origin IP is hidden behind Cloudflare's proxy — direct IP bypass is not viable

### Known TODO (for when this resumes)

- `buildAbstract()` in the Worker is a placeholder encoding PAC metadata into the OJS abstract field. Once the PAC form captures a real abstract from authors, replace with: `return pac.abstract || '';`
- Wire up a "Submit to PAC" button in `index.html` that POSTs form data to the Worker URL
- Consider automating Worker deployment via GitHub Actions + Wrangler CLI

## Security recommendations

### API token (OJS)

- **Never commit an OJS API token to this repository.** The repo is public; anything committed is permanently visible in git history even if later deleted.
- Store the token only in Cloudflare's encrypted secret store (`OJS_TOKEN` variable in the Worker settings). It is never transmitted to the browser or logged.
- **Rotate the token periodically**, and immediately if it is ever accidentally exposed (e.g. pasted into a chat, email, or issue). Regenerate under User Profile → API Key in OJS.
- The token belongs to a PAC service/admin account. Limit that account's OJS permissions to the minimum needed for submission creation if OJS's role system allows it.

### GitHub repository

- This repo is intentionally public (required for free GitHub Pages hosting). Do not commit any credentials, API keys, or tokens here — not even in comments, commit messages, or configuration files.
- `form-schema.json` is generated and committed automatically by GitHub Actions. Review Actions logs if a build fails unexpectedly.
- `GITHUB_TOKEN` (used by the Actions workflow to push `form-schema.json`) is automatically scoped to this repo only and expires after each run. No additional secrets are needed for the build pipeline.

### Cloudflare Worker

- The `ALLOWED_ORIGIN` variable restricts which domains the Worker accepts requests from. Keep this set to the exact GitHub Pages origin (`https://sgarrettroe.github.io`) — do not set it to `*`.
- The Worker validates the `Origin` header on every request. Direct `curl` calls (without a browser-matching Origin) are rejected.
- Worker source code (`pac-ojs-worker.js`) is safe to store publicly — it contains no secrets, only logic.
- Monitor Worker usage in the Cloudflare dashboard. Unexpected spikes in request volume could indicate misuse.

### OJS instance

- The PAC OJS instance (`pac.pogil.org`) is behind Cloudflare's Managed Challenge, which blocks automated non-browser requests to `/api/v1/*`. This is a useful layer of protection — do not disable it.
- If you need to allow the Cloudflare Worker to bypass the challenge (for the API path only), add a Cloudflare WAF rule that exempts requests originating from Cloudflare Workers on the `/index.php/pac/api/v1/*` path, rather than disabling the challenge globally.
